# NotesFlare V1.1 — Integration Bridge Guide

> **AI Instruction File: Frontend ↔ Backend Integration**
> This file defines the exact contract between the V1.1 frontend and backend, the data flow for every user action, error handling at the boundary, and how to verify both layers work correctly together. Read `V1.1_BACKEND.md` and `V1.1_FRONTEND.md` before this file.
> This file does NOT introduce new code. It describes how the code in those two files connects and must be verified.

---

## 0. PURPOSE OF THIS FILE

Building frontend and backend independently is not enough. Integration failures are their own category of bug:

- A frontend sends `text: ""` on an empty delta — the backend rejects it as 400
- The backend returns `has_session: false` — the frontend renders EmptyState when it should show the last Flareon
- The session resume races with the sidebar flareon list — the active Flareon is highlighted wrong
- The append-only model accumulates duplicates if the frontend's delta tracking drifts

This file defines the complete contract at each integration point and verifies it end-to-end.

---

## 1. THE INTEGRATION SURFACE

There are exactly 6 points where frontend and backend communicate:

| # | Trigger | Frontend call | Backend endpoint | Response shape |
|---|---|---|---|---|
| 1 | App startup | `api.resumeSession()` | `GET /api/session/resume` | `SessionResumeResponse` |
| 2 | Sidebar Flareon click | `api.switchFlareon(id)` | `GET /api/session/switch/{id}` | `FlareonSwitchResponse` |
| 3 | Sidebar load | `api.listFlareons()` | `GET /api/flareons` | `{flareons: Flareon[]}` |
| 4 | New Flareon creation | `api.createFlareon(name)` | `POST /api/flareons` | `Flareon` |
| 5 | Typing → autosave | `api.appendChunk(id, delta)` | `POST /api/burst/append` | `AppendChunkResponse` |
| 6 | Archive page load | `api.openFlareon(id)` | `GET /api/flareons/{id}` | `FlareonDetail` |

Each integration point is described in full below.

## 2. INTEGRATION POINT 1: SESSION RESUME

### When it fires
Once on app startup, inside `useSession.initSession()`. It fires in parallel with `listFlareons()` using `Promise.all`.

### Request
```
GET http://127.0.0.1:8000/api/session/resume
```

No body. No query params.

### Expected response: first-time user
```json
{
  "has_session": false,
  "flareon": null,
  "burst_id": null,
  "stream_content": "",
  "started_at": null
}
```

### Expected response: returning user
```json
{
  "has_session": true,
  "flareon": {
    "id": 3,
    "name": "Thermodynamics",
    "created_at": "2025-01-15T10:00:00+00:00",
    "last_opened_at": "2025-01-15T14:30:00+00:00"
  },
  "burst_id": 7,
  "stream_content": "The second law states that entropy...",
  "started_at": "2025-01-15T14:00:00+00:00"
}
```

### Frontend behavior by response
| Condition | Frontend renders |
|---|---|
| `has_session: false` | `EmptyState` — "Select a Flareon to begin." |
| `has_session: true` | `StreamShell` with `StreamInput` pre-loaded with `stream_content` |
| Network error | `EmptyState` with console error (silent failure to user) |

### Critical integration invariant
`stream_content` must be the **full reconstructed content** of the active burst — all chunks concatenated in order. The frontend trusts this completely and sets the stream input's `defaultValue` to it. If the backend returns partial content, the user will see truncated text and any subsequent appends will duplicate content.

**Verify:** Create a Flareon, type "Hello ", wait 1s (autosave fires), type "world", wait 1s, restart the backend, call `GET /api/session/resume`. `stream_content` must be `"Hello world"`.

## 3. INTEGRATION POINT 2: FLAREON SWITCH

### When it fires
When the user clicks any Flareon in the sidebar — inside `useSession.switchFlareon(id)`.

### Request
```
GET http://127.0.0.1:8000/api/session/switch/{flareonId}
```

### Expected response
```json
{
  "flareon": { "id": 2, "name": "Startup Ideas", ... },
  "burst_id": 5,
  "stream_content": "The freemium model fails when...",
  "started_at": "2025-01-15T09:00:00+00:00"
}
```

### Frontend behavior
1. Receives response
2. Calls `api.listFlareons()` to refresh sidebar order (most-recently-opened first)
3. Sets `activeFlareon`, `activeBurstId`, `streamContent`, `burstStartedAt` in session state
4. The `key` prop on `StreamShell` changes → React unmounts old `StreamInput`, mounts new one with `initialContent = stream_content`
5. New `StreamInput` auto-focuses with cursor at end

### Critical integration invariant
The `key` prop on `StreamShell` is `${activeFlareon.id}-${activeBurstId}`. If either changes, the stream input resets. This means: switching to a Flareon where the backend creates a new burst (30-min window expired) correctly resets the input to empty.

**Verify:** Open Flareon A, type something, switch to Flareon B, switch back to Flareon A. The stream input must show Flareon A's content exactly.

- After `createFlareon`

### Request
```
GET http://127.0.0.1:8000/api/flareons
```

### Expected response
```json
{
  "flareons": [
```

Ordering: most-recently-opened first, then nulls last sorted by creation.

The `Sidebar` receives `flareons` and `activeFlareonId`. The active Flareon is highlighted. The user can click any item to switch.

**Verify:** Create 3 Flareons. Open them in order A, B, C. The sidebar must list them C, B, A.

## 5. INTEGRATION POINT 4: CREATE FLAREON

### When it fires
When the user presses Enter in the sidebar's new-Flareon input.

### Full flow (frontend)
```
createFlareon("My New Flareon")
  → api.createFlareon("My New Flareon")       POST /api/flareons
  → api.listFlareons()                         GET /api/flareons
  → find created Flareon in list by name
  → switchFlareon(created.id)                  GET /api/session/switch/{id}
```

### Why find by name instead of by returned ID
`api.createFlareon` returns the new `Flareon` object including its ID. The simpler flow would be: use the returned ID directly for `switchFlareon`. This is acceptable and preferred. The `useSession.createFlareon` implementation can be simplified:

```typescript
async function createFlareon(name: string): Promise<void> {
  const newFlareon = await api.createFlareon(name);
  // Use the returned ID directly — no need to re-fetch the list first
  await switchFlareon(newFlareon.id);
}
```

### Edge cases
| Condition | Backend response | Frontend behavior |
|---|---|---|
| Empty name | 400 `Flareon name cannot be empty.` | Show error inline in sidebar input |
| Duplicate name | 400 `A Flareon named 'X' already exists.` | Show error inline in sidebar input |
| Success | 201 with Flareon object | Input clears, new Flareon opens in stream |

The sidebar must display the error message inline under the input, using `data-testid="flareon-name-error"`. The error must clear when the user starts typing again.

## 6. INTEGRATION POINT 5: APPEND CHUNK (AUTOSAVE)

This is the highest-frequency integration point. It fires every ~1 second while the user is typing.

### When it fires
Inside `useAutosave.scheduleAppend()`. The timer resets on every keystroke. When 1 second of inactivity passes, the delta is sent.

### The delta computation
The delta is computed by `useStreamBuffer.getDeltaSinceLastSync()`:

```typescript
getDeltaSinceLastSync = () => bufferRef.current.slice(lastSyncedLength)
```

Where `lastSyncedLength` is the length of `bufferRef.current` at the time of the last successful save.

**Critical:** `lastSyncedLength` is updated only by `markSynced()`, which is called only after `api.appendChunk` succeeds. If the save fails, `lastSyncedLength` does not advance. On the next save attempt, the delta will include the unsaved text — content is never lost.

### Request
```json
POST /api/burst/append
{
  "burst_id": 7,
  "text": " states that entropy"
}
```

Note: `text` is the **delta only**, not the full content.

### Expected response
```json
{
  "success": true,
  "sequence_number": 3
}
```

### Guard: empty delta
Before calling `api.appendChunk`, `useAutosave` checks:
```typescript
const delta = getDelta();
if (!delta) return;
```

This prevents sending empty strings. The backend also rejects empty strings with 400, but the frontend guard avoids the round-trip entirely.

### Content reconstruction contract
The backend reconstructs content as:
```
chunk[seq=0] + chunk[seq=1] + chunk[seq=2] + ...
```

This is a simple string concatenation. The frontend never sends overlapping content. The invariant is:

```
bufferRef.current === all_chunks_concatenated_in_order
```

If this invariant breaks (e.g., two browser tabs, or a sync bug in `lastSyncedLength`), content will duplicate or corrupt. V1.1 does not need to handle multiple-tab scenarios. The invariant is maintained as long as a single `StreamInput` instance owns the buffer.

**Verify:** Type "Hello " (6 chars), wait 1s → append fires with `"Hello "`. Type "world" (5 chars), wait 1s → append fires with `"world"`. Call `GET /api/session/resume`. `stream_content` must be `"Hello world"`.

## 7. INTEGRATION POINT 6: ARCHIVE PAGE

### When it fires
When the user navigates to `/flareon/{id}` via the Archive button in `NavControls`.

### Request
```
GET http://127.0.0.1:8000/api/flareons/{id}
```

This is the existing V1 endpoint, unchanged in V1.1.

### Expected response
```json
{
  "flareon": { "id": 3, "name": "Thermodynamics", ... },
  "bursts": [
    { "id": 1, "flareon_id": 3, "started_at": "2025-01-14T10:00:00+00:00", "content": "First session content" },
    { "id": 7, "flareon_id": 3, "started_at": "2025-01-15T14:00:00+00:00", "content": "Second session content" }
  ],
  "active_burst_id": 7
}
```

In V1.1, `content` in each burst is the fully reconstructed concatenation of all chunks. This is assembled by `stream_service.reconstruct_burst()` inside `burst_service.get_all_bursts_for_flareon()`.

**Verify:** After typing across two sessions (two separate bursts), navigate to the archive page. Both bursts must appear with complete content, separated by `BurstDivider` components.

## 8. ERROR HANDLING CONTRACT

Every integration point must handle failures. This table defines exactly what the frontend does when the backend returns an error or is unreachable.

| Integration point | Error | Frontend behavior |
|---|---|---|
| `resumeSession` | Network error | Load with `has_session: false`, show EmptyState, log error |
| `resumeSession` | 500 | Same as network error |
| `switchFlareon` | 404 | Log error, do not change active Flareon, do not crash |
| `switchFlareon` | Network error | Same as 404 |
| `listFlareons` | Any error | Show empty sidebar, log error |
| `createFlareon` | 400 duplicate | Show error message under input |
| `createFlareon` | 400 empty | Show error message under input |
| `appendChunk` | Any error | Silent failure, retry on next keystroke |
| `appendChunk` | Empty delta (guarded) | No request sent at all |
| `openFlareon` (archive) | 404 | Show "Flareon not found." in archive page |

**The one rule:** typing must NEVER be interrupted. `appendChunk` errors are always silent to the user.

## 9. STARTUP SEQUENCE — DETAILED TIMELINE

This is what must happen, in order, every time the app opens:

```
1. Electron boots
2. Python backend starts (main.py)
   → DB initialized
   → Migration runs if needed
   → uvicorn listening on 127.0.0.1:8000
3. Next.js frontend loads
4. StreamPage mounts
5. useSession.initSession() fires
   → Promise.all([
       api.listFlareons(),         ← parallel
       api.resumeSession(),        ← parallel
     ])
6. Both responses arrive
7. State updates:
   → flareons = [list]
   → activeFlareon = resume.flareon (or null)
   → activeBurstId = resume.burst_id (or null)
   → streamContent = resume.stream_content
   → burstStartedAt = resume.started_at
   → isLoading = false
8. StreamPage re-renders
   → LoadingScreen unmounts
   → Sidebar renders with flareon list
   → StreamShell renders with activeFlareon
9. StreamInput mounts
   → defaultValue = streamContent
   → autoFocus fires
   → cursor placed at end of existing content
10. User can type immediately
```

**Target for step 1 → step 10:** < 1.5 seconds total.

**Backend must be running before the frontend calls it.** In Electron, the main process starts Python and polls `/api/health` before loading the Next.js page. This is defined in `05_ELECTRON_SHELL.md` and is not changed by V1.1.

## 10. THE BURST CONTINUITY INTEGRATION

The 30-minute rule lives entirely in the backend (`burst_service.get_or_create_active_burst`). The frontend is unaware of it. Here is how it surfaces at the integration boundary:

### Scenario A: User returns within 30 minutes
1. `GET /api/session/resume` → `burst_id: 7` (same burst as last time)
2. `stream_content`: full accumulated content of burst 7
3. Frontend loads that content into StreamInput
4. User continues typing — appends to burst 7
5. ✓ Correct: seamless continuation

### Scenario B: User returns after 30+ minutes
1. `GET /api/session/resume` → `burst_id: 8` (new burst created by backend)
2. `stream_content: ""` (new burst is empty)
3. Frontend loads empty string into StreamInput
4. User starts typing from scratch — appends to burst 8
5. `BurstTimeline` on archive page will show burst 7 (old) and burst 8 (new)
6. ✓ Correct: invisible new session

### What the frontend MUST NOT do
- Try to detect the 30-minute gap itself
- Show any notification about a new burst being created
- Modify the burst ID it received from the backend

The frontend trusts the backend's `burst_id` completely.

## 11. DELTA TRACKING EDGE CASES

The append model requires careful delta tracking. These edge cases must be handled:

### Case 1: User deletes characters
```
Buffer before: "Hello world"   lastSyncedLength: 6  (after "Hello " was saved)
User deletes "rld": buffer becomes "Hello wo"
getDeltaSinceLastSync() = "Hello wo".slice(6) = "wo"
→ append "wo" to burst
→ reconstructed content: "Hello " + "wo" = "Hello wo"
✓ Correct
```

### Case 2: User deletes all typed text
```
Buffer before: "Hello world"   lastSyncedLength: 6
User selects all and deletes everything: buffer becomes ""
getDeltaSinceLastSync() = "".slice(6) = ""  (empty string!)
→ guard fires: if (!delta) return
→ no append
→ reconstructed content: "Hello " (only what was saved)
⚠ Content divergence: buffer is "" but backend has "Hello "

On next keystroke: buffer = "X", lastSyncedLength = 6
delta = "X".slice(6) = ""  ← still empty!
→ no append
```

This is a known limitation of the delta model when the user deletes past the last sync point. In V1.1, **this is acceptable**. The design document (09_STREAM_PAGE.md) states the stream is append-oriented. Full delete-and-retype is an edge case.

**Do not try to fix this in V1.1.** The correct fix (send full content on any deletion) is a V1.2 concern.

### Case 3: Rapid typing then immediate close
```
User types "Hello world" quickly, closes app before 1s autosave fires
→ No append call was made
→ Content is lost

This is the only real data loss scenario in V1.1.
```

Mitigation: add a `beforeunload` / window close handler that calls `appendChunk` synchronously. This is in scope for the polish pass (Phase G) but not the core implementation.

## 13. INTEGRATION ANTI-PATTERNS TO AVOID

These are integration-specific bugs that don't show up in unit tests but will appear in the combined system.

**Anti-pattern 1: Frontend caches burst content**
If `StreamShell` stores `initialContent` in React state and only updates it on prop change, switching to the same Flareon twice in a row will use stale cached content. Always derive from `useSession.streamContent` directly.

**Anti-pattern 2: appendChunk race condition**
If the user types quickly and the 1s timer fires while another append is in flight:
- `getDelta()` returns correct text (from `lastSyncedLength` which hasn't advanced yet)
- Two appends fire with overlapping content
- Content is duplicated

The `useAutosave` timer-reset-on-keystroke pattern prevents this: if the user is still typing, the timer resets and no append fires. The race only occurs if the user stops typing, then immediately starts typing again within the same second window and the first append is slow. This is an edge case that V1.1 accepts.

**Anti-pattern 3: Flareon list out of sync with active Flareon**
The `listFlareons()` call in `switchFlareon` is for sidebar ordering only. The active Flareon state comes from the `switchFlareon` API call, not from the list. These must not be confused.

**Anti-pattern 4: Double-mounting StreamInput on session resume**
If `StreamPage` renders twice during hydration (a Next.js edge case with `"use client"`), `StreamInput` might mount twice and focus twice. The `key` prop on `StreamShell` prevents this: as long as `activeFlareon.id` and `activeBurstId` don't change, no remount occurs.
